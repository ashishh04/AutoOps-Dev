Here are the three built out to the same contract, plus the parts that usually break.

---

# 1. Alert Quality Agent

The only agent in the set that operates on your alerting *system* rather than on incidents. It runs on a schedule, not on events.

**Trigger:** nightly batch over a rolling 30d window, plus on-demand before an alert rule PR merges.

**Inputs**
- Alert fire/clear history per rule (not per incident)
- Incident records with `detection_source` (alert / customer / manual / synthetic)
- Action log: what anyone or anything actually did between page and resolve
- Dedupe decisions from the Correlation Agent
- Page delivery outcomes from the Escalation Agent (acked, timed out, escalated)
- Rule metadata: owner, severity, compliance-mandated flag, as-code source path

**Core metrics per rule**

| Metric | Definition | Why it matters |
|---|---|---|
| Actionability rate | fires where a state-changing action followed | the real precision proxy |
| Auto-resolve rate | fires that cleared with zero action | flapping or self-healing |
| Duplicate ratio | fires absorbed into an existing incident | correlation is already handling it |
| Flap index | fire→clear cycles per hour | needs `for:` duration, not a threshold change |
| Off-hours noise | 22:00–08:00 pages with no action | weight this 3–5× |
| MTTA | page to ack | routing problem or fatigue signal |
| Detection gap contribution | incidents with `detection_source != alert` touching this service | the false-negative side |

**Output**

```
rule_id, window, quality_score(0-100), verdict,
evidence[{metric, value, percentile_vs_fleet}],
recommendation{type, params, est_noise_reduction, est_recall_risk},
confidence
```

Recommendation types worth supporting: `raise_threshold`, `add_for_duration`, `add_dependency_suppression`, `demote_to_ticket`, `convert_to_slo_burn_rate`, `merge_with_sibling`, `retire`, `no_change`.

**The hard part.** Recall is not observable from alert data. You can only learn about misses from incidents found some other way, which means `detection_source` has to be a mandatory field on every incident, enforced at close. Without it this agent will confidently recommend deleting the only rule that would have caught the next outage.

**Anti-gaming.** Quality score alone is trivially improved by suppressing everything. Always report it paired with detection-gap count for the same service, and never let a single number be the team's target.

**Guardrails.** Proposes only, by default. If you allow autonomous action, restrict it to opening a PR against alerts-as-code with the diff and evidence attached. Never touch rules flagged compliance-mandated. Require a minimum sample (say 20 fires) before any retirement recommendation.

**Idempotency:** `hash(rule_id + window_end + recommendation_type)`. Dismissals persist with a TTL so the agent doesn't re-file the same finding weekly.

**Fallback:** insufficient sample → emit `no_change` with `reason: low_volume`, not silence.

# 2. Cost / FinOps Agent

**Trigger:** daily on billing ingest, hourly on near-real-time usage, and event-driven on deploy/scale/provision events.

**Inputs**
- Billing export (FOCUS or CUR), which lags 6–24h and is *revised retroactively*
- k8s requests/limits vs actual p95 usage per workload
- Tag/label allocation map, plus the untagged bucket
- Commitment inventory: RIs, savings plans, CUDs, expiry dates, coverage
- Change events from the Change Detection Agent
- SLO headroom from the burn-rate agent
- A unit denominator: requests, tenants, orders, GB ingested

**Think in unit cost, not absolute cost.** Without a denominator, every growth quarter looks like a regression and the agent files noise. `cost_per_unit` is the primary series; absolute spend is secondary.

**Sub-capabilities, roughly in build order**

1. **Allocation** — % unallocated spend, per-service showback. Nothing else works until this is under ~10%.
2. **Spend anomaly + attribution** — reuse your anomaly detection on cost series, then join to change events within the window. "Spend up 40% on service X, correlated with deploy abc123 at 14:02" is the output that gets acted on. A spike with no attribution gets a lower confidence.
3. **Rightsizing** — requests vs p95+headroom. Must consume SLO headroom before recommending.
4. **Waste sweep** — unattached volumes, aged snapshots, orphaned LBs and IPs, idle non-prod, zombie preview environments, oversized dev clusters.
5. **Commitment coverage** — uncovered steady-state on-demand, expiring commitments, over-commitment risk.
6. **Retention and tiering** — worth flagging for you specifically: on an observability platform, telemetry storage and ingest are frequently a top-three line item. Log retention, metric cardinality, and trace sampling rates are legitimate cost findings, and cardinality explosions usually trace back to a single bad label.
7. **Egress** — cross-AZ and cross-region chatter, often an accidental topology problem.
8. **Forecast and budget burn** — with the same multi-window burn-rate logic you use for SLOs.

**Output**

```
finding_id, category, resource_ref, est_monthly_savings,
risk_tier(low|med|high), confidence, evidence[],
remediation{action, reversible, requires_slo_check},
data_freshness{billing_through, is_partial}
```

Sort the backlog by `savings / risk`, not savings alone.

**Guardrails.** This is the agent most likely to cause an outage. Rules I'd hard-code:
- Non-prod before prod, always. Separate autonomy tiers per environment.
- No scale-down recommendation without current SLO headroom, and none at all during an open incident or change freeze.
- Cap any single action's blast radius (one workload, one AZ).
- Deletions of stateful resources are suggest-only, permanently. Snapshots and volumes come back to haunt people.

**Idempotency:** `hash(resource_arn + finding_category + billing_period)`. Critical here — daily runs will otherwise reopen the same 400 tickets.

**Fallback:** billing incomplete or revised → emit findings with `is_partial: true` and suppress anomaly alerts entirely rather than firing on a half-loaded day. Late-arriving cost data is the single biggest source of false positives in this agent.

# 3. Escalation & Routing Agent

**Trigger:** incident declared, severity change, ack timeout, burn-rate acceleration, responder unavailable.

**Inputs**
- Service catalog / CMDB ownership
- On-call schedules, overrides, holidays, time zones
- Ranked root cause + member services from the Correlation and RCA agents
- Blast radius and severity
- Responder state: current open incidents, pages in last 7d, ack history
- Expertise map, derived from who resolved similar incidents before
- Notification channel policy per severity

**Decisions it owns**

1. **Which team.** Page the owner of the *ranked root cause*; notify, don't page, the owners of symptom services. Get this wrong and a single correlated incident wakes six teams, which is the failure mode that makes people distrust the whole platform.
2. **Which human.** Rotation → override → escalation policy, with load-awareness as a tiebreak when the rotation has multiple eligible responders.
3. **Which channel.** Ticket / chat / push / phone, mapped from severity × time-of-day × burn rate.
4. **When to escalate.** Unacked timer (severity-scaled), burn-rate acceleration, or explicit request. Escalation depth capped.
5. **When to widen.** Multi-team incident → summon an incident commander rather than paging more engineers laterally.
6. **When not to page at all.** Maintenance window, low burn rate, ticket-tier rule, already-acked duplicate.

**Output**

```
incident_id, escalation_level, target{team, user, channel},
rationale{ownership_source, root_cause_service, confidence},
timers{ack_deadline, next_escalation_at},
suppressed{bool, reason}
```

**Hard parts**
- **Ambiguous ownership.** Multiple candidate owners, or none. Resolution order: explicit service annotation → catalog → repo CODEOWNERS → last deployer → default escalation path.
- **Ack deduplication** across chat, mobile, and phone. Ack is a single state on the incident, not per-channel.
- **Rotation boundary mid-incident.** Don't reassign an active incident silently; hand off explicitly with the outgoing responder notified, or hold them until relieved.
- **Fatigue.** Track pages per responder per week and off-hours pages specifically. Rebalance where the schedule permits, and emit the fatigue signal to the Alert Quality Agent, which is where the actual fix lives.

**Guardrails.** The non-negotiable one: **never silently drop a page.** Unresolvable ownership must fall through to a default escalation path with a loud "routing failed" annotation. Every other guardrail is secondary to this. Beyond that: rate-limit executive notification, cap auto-escalation depth, and make suppression decisions fully auditable with the rule that caused them.

**Idempotency:** `hash(incident_id + escalation_level + target)`. Retries and restarts double-page without it.

**Feedback metric:** routing accuracy = 1 − reassignment rate. Reassignments are cheap to capture and are the single best proxy for whether your ownership data is real or aspirational.

---

## How the three close a loop

Escalation emits page outcomes and fatigue → Alert Quality consumes them as its actionability and noise signals → its rule changes reduce page volume → Escalation's accuracy improves because there's less to route. Meanwhile FinOps depends on SLO headroom from the same detection layer, and its own actions must be published back as change events so the Correlation Agent can blame them when something breaks twenty minutes later. That last one is easy to forget and causes genuinely baffling incidents.

## Versioning rules

Three that keep this stable as you add agents:

1. **Additive-only within a major.** New optional fields, new enum members at the end. Consumers ignore unknown fields rather than rejecting.
2. **Enum extension is a minor bump, enum removal is major.** Handlers need a `default:` branch for unrecognized values — particularly `finding.type`, `recommendation.type`, and `remediation.action`.
3. **`idempotency_key` composition is frozen at the major version.** Changing what goes into the hash silently reopens every finding you've ever closed.

Happy to write the guardrail policy schema that sits in front of every write action — the one that maps confidence band × environment × risk tier to a granted autonomy tier — or put this whole set in a doc so you can iterate on it.

guardrails

Here's the layer that sits in front of every write. Five parts: where it lives, the policy document, evaluation semantics, the decision record, and a worked instance covering the three agents.

---

## 1. Where it sits

Not a library agents call. A service in the call path, between verdict emission and tool execution:

```
agent → verdict → [POLICY ENGINE] → reservation → executor → change_event
                        ↓
                  decision record (always written, allow or block)
```

Four properties that have to hold, or the rest is decoration:

- **Deny by default.** No matching rule is a block, not an allow.
- **Fail closed.** Engine timeout, missing precondition data, unreachable authority → block. A guardrail that fails open is worse than none, because people trust it.
- **Preconditions are re-evaluated, never trusted.** The agent's verdict says `no_open_incident: satisfied`. The engine ignores that field and asks the incident store itself. Self-attested preconditions are the single most common way this layer gets quietly bypassed.
- **Monotonic downgrade only.** Rules can lower the granted tier. No rule can raise it above what an earlier rule granted. This makes evaluation order-independent for safety, which is what lets you add rules without re-auditing the whole set.

## 3. Evaluation semantics

Deterministic, in this order. Written as pseudocode because the ordering is the actual specification:

```
evaluate(verdict, action):

  1.  schema_valid(verdict, action)            else BLOCK(schema_violation)
  2.  resolve environment from authority       else environment = "unknown"
  3.  tier = tier_matrix.lookup(
              confidence_band, environment, risk_tier,
              blast_radius_scope, time_of_day)
      tier = min(tier, ceiling.global,
                       ceiling.by_environment[env],
                       ceiling.by_agent[agent],
                       action_class.max_tier)

  4.  for each rule where when(...) matches:          # order irrelevant
        block            -> BLOCK(rule_id)            # terminal, short-circuit
        downgrade_to      -> tier = min(tier, rule.downgrade_to)
        require_precond   -> collect
        require_approval  -> collect
        annotate          -> collect

  5.  for each collected precondition:
        result = query(authority, max_staleness_s)     # live, not from verdict
        unsatisfied      -> BLOCK(precondition_failed, check)
        lookup_failed    -> BLOCK(precondition_unavailable, check)   # fail closed

  6.  budgets: reserve(action) atomically
        exhausted -> on_exhaustion (BLOCK | tier = suggest)

  7.  if tier >= act_with_approval and approval required:
        approval_valid_for_this_action_id?  else BLOCK(approval_missing)

  8.  if tier in {observe, suggest}: ALLOW_AS_PROPOSAL
      else:                          ALLOW_WITH_TIER(tier)

  9.  write decision record, always, both paths
```

Three things worth calling out:

**Step 4 is order-independent.** Because `downgrade_to` uses `min()` and `block` short-circuits, you get the same answer regardless of rule order. `priority` exists only so the decision record can name the *most specific* rule for human reading.

**Step 5 runs after step 4** on purpose. Rules determine which preconditions apply; you don't want to pay for live SLO lookups on actions a rule already blocked.

**Step 6 reserves rather than checks.** Two agents evaluating concurrently against a budget of one will both see capacity if you only read. Reserve with a TTL, confirm on execution, release on failure.

The policy is code, so it gets tests. A minimal harness shape:

The cases I'd insist on before this goes near production:

- Every `immutable` rule has a test proving break-glass doesn't lift it
- Unknown environment resolves to `suggest`, never higher
- Every precondition authority has a test where lookup fails → block
- Budget exhaustion under concurrent reservation
- An approval from the requesting identity is rejected
- An approval bound to action A is rejected for action B
- A fallback verdict at confidence 0.99 still lands on `observe`
- The empty policy (no matching rule) blocks

That last one catches the regression that matters most — someone refactors the matcher, nothing matches any more, and without the test the system fails open while every dashboard looks green.

## Model

Three concepts, and conflating any two of them is where this usually goes wrong:

- **Verdict** — one emission from one agent run. Immutable, disposable after ingest.
- **Observation** — an accepted verdict, persisted. Append-only.
- **Finding** — the durable entity keyed by `idempotency_key`, carrying lifecycle state, dismissal, and counters. Mutable head over an append-only tail.

`POST /findings` takes a verdict and returns what it did with it. The agent side becomes testable the moment that disposition is explicit.

## 2. Write path

Two distinct hashes. `idempotency_key` answers *is this the same finding*. `content_hash` answers *has the substance changed*. Keeping them separate is what lets a dismissed finding stay quiet while its numbers drift, and resurface when they don't just drift.

`content_hash` is computed over the fields that would change a human's decision, bucketed to stop noise:

| Agent | Content hash covers |
|---|---|
| alert-quality | `recommendation.type`, normalised `params`, `verdict_class` |
| finops | `remediation.action`, `risk_tier`, `est_monthly_savings.amount` bucketed to ±25% log bands |
| escalation | `targets[].team_ref`, `escalation_level`, `suppressed.rule_type` |

The disposition table — this is the contract:

| Incoming | Current state | Disposition | Notify |
|---|---|---|---|
| new key | — | `created` | yes, if not suppressed by scope rule |
| same key, same content | `open` / `acknowledged` | `no_change` (touch only) | no |
| same key, material change | `open` / `acknowledged` | `updated` | if severity or priority crossed a band |
| same key, same content | `suppressed`, TTL live | `suppressed` | no |
| same key, same content | `suppressed`, TTL expired | `reopened` | yes |
| same key, material change | `suppressed`, TTL live, `survives_material_change = false` | `reopened` | yes |
| same key, material change | `suppressed`, TTL live, `survives_material_change = true` | `suppressed` | no |
| same key, any content | `resolved` | `reopened`, `episode_count++` | yes, as regression |
| same key, any content | `stale` | `reopened` | yes |
| same `verdict_id` seen before | any | `duplicate_verdict` | no |

Single-statement upsert, because two agent replicas will race:

```sql
INSERT INTO finding (
  tenant_id, idempotency_key, idempotency_key_version, content_hash,
  agent_name, agent_version, category, subject_kind, subject_id,
  service_ref, environment, severity, risk_tier, confidence,
  confidence_band, priority_score, first_seen_at, last_seen_at,
  last_material_change_at, state_changed_at, updated_at, payload, last_run_id
) VALUES (...)
ON CONFLICT (tenant_id, idempotency_key, idempotency_key_version) DO UPDATE SET
  last_seen_at     = EXCLUDED.last_seen_at,
  occurrence_count = finding.occurrence_count + 1,
  agent_version    = EXCLUDED.agent_version,
  last_run_id      = EXCLUDED.last_run_id,

  content_hash = CASE WHEN finding.content_hash IS DISTINCT FROM EXCLUDED.content_hash
                      THEN EXCLUDED.content_hash ELSE finding.content_hash END,
  payload      = CASE WHEN finding.content_hash IS DISTINCT FROM EXCLUDED.content_hash
                      THEN EXCLUDED.payload ELSE finding.payload END,
  last_material_change_at = CASE WHEN finding.content_hash IS DISTINCT FROM EXCLUDED.content_hash
                      THEN EXCLUDED.last_seen_at ELSE finding.last_material_change_at END,
  material_change_count = finding.material_change_count +
                      CASE WHEN finding.content_hash IS DISTINCT FROM EXCLUDED.content_hash
                      THEN 1 ELSE 0 END,

  episode_count = finding.episode_count +
                      CASE WHEN finding.state IN ('resolved','stale') THEN 1 ELSE 0 END,
  updated_at    = EXCLUDED.updated_at
RETURNING finding_id, state, content_hash, episode_count,
          (xmax = 0) AS was_insert;
```

State resolution and the transition row run in the same transaction, driven by the returned `was_insert` and whether `content_hash` moved.

**Don't write an observation on `no_change`.** Alert Quality sweeps every rule nightly and 95% of those are `no_change`; writing an observation each time buys you nothing and costs you a table you have to prune weekly. Write observations only on `created`, `updated` with `is_material = true`, and `reopened`. The head `payload` plus `last_seen_at` covers the rest. If you want a sampled trail, write one non-material observation per finding per week and accept the gap.

## 3. Dismissal and TTL

Default TTLs, overridable per dismissal:

| Category | Default TTL | Rationale |
|---|---|---|
| `alert_quality` | 90d | rule behaviour changes slowly |
| `rightsizing` | 30d | utilisation shifts |
| `waste` | 14d | orphans should be re-checked |
| `spend_anomaly` | 7d | short-lived by nature |
| `commitment_coverage` | until expiry date | anchored to a real event |
| `allocation_gap` | 30d | |

Permanent dismissal (`expires_at IS NULL`) requires an elevated role and a `reason_code` from a closed set — `by_design`, `compensating_control`, `accepted_risk`, `false_positive`. Free-text-only permanent dismissals are how a backlog quietly becomes fiction.

Expiry is handled by a sweeper rather than computed at read, so that `GET` stays a single index scan and the reopen produces a real transition row someone can see:

```sql
UPDATE finding f SET
  state = 'open', state_changed_at = now(), updated_at = now(),
  state_reason = 'suppression_expired'
FROM finding_suppression s
WHERE s.finding_id = f.finding_id
  AND s.revoked_at IS NULL
  AND s.expires_at <= now()
  AND f.state = 'suppressed'
  AND NOT EXISTS (   -- no other live suppression covers it
    SELECT 1 FROM finding_suppression s2
    WHERE s2.revoked_at IS NULL
      AND (s2.expires_at IS NULL OR s2.expires_at > now())
      AND covers(s2, f)
  )
RETURNING f.finding_id;
```

Scope precedence on ingest: `finding` → `subject_category` → `service_category` → `category_global`. First live match wins, and the winning `suppression_id` goes on the transition row. Without that, nobody can answer why a finding never appeared.

## 4. Staleness, and the trap in it

A finding that stops being emitted should close. But absence of a verdict has two causes — the problem went away, or the agent crashed. Reaping on `last_seen_at` alone means an agent outage silently marks your whole backlog resolved, and it looks like a great week.

Reap only against a **completed run whose `subject_scope` covers the finding's subject**:

```sql
WITH covering_runs AS (
  SELECT DISTINCT ON (agent_name) agent_name, completed_at, subject_scope
  FROM agent_run
  WHERE tenant_id = $1 AND status = 'complete'
  ORDER BY agent_name, completed_at DESC
)
UPDATE finding f SET
  state = 'stale', state_changed_at = now(), updated_at = now(),
  state_reason = 'not_reobserved'
FROM covering_runs r
WHERE f.tenant_id = $1
  AND f.agent_name = r.agent_name
  AND f.state IN ('open', 'acknowledged')
  AND f.last_seen_at < r.completed_at - interval '1 minute'
  AND scope_covers(r.subject_scope, f.subject_kind, f.subject_id)
  AND f.last_seen_at < now() - (
        SELECT reap_after FROM category_policy WHERE category = f.category)
RETURNING f.finding_id;
```

`status = 'partial'` never reaps. A run that covered 40% of subjects tells you nothing about the other 60%.

`stale` and `resolved` are deliberately different states. `resolved` means someone or something acted. `stale` means it stopped being observed and nobody knows why. Collapsing them destroys the only signal that distinguishes "we fixed it" from "it stopped alerting".

## 6. What will break

**Key composition changes.** You froze `idempotency_key` composition at the major version, which is right, but an agent author will eventually change what goes into the hash and every existing finding will silently fork into a duplicate. That's why `idempotency_key_version` is in the unique constraint rather than buried in the payload. Bumping it is a declared migration: run both versions in shadow for one cycle, write `superseded` transitions from old to new via a `finding_link` table, then retire the old version. Detect an undeclared bump by alerting when a single `(subject_id, category)` pair suddenly holds two open findings from the same agent.

**Dismissal scope leakage.** `service_category` dismissals are convenient and quietly enormous. Cap their TTL lower than finding-scope ones (14d, say), require a role, and surface them in the weekly digest by count of findings they're currently hiding.

**Observation growth.** Even with `no_change` suppressed, FinOps at resource granularity will produce millions of rows a year. Monthly partitions, drop after 13 months, and keep the head payload on `finding` so detaching an old partition never breaks the current view.

**Materiality tuning.** Too tight and dismissed findings resurface on every ±2% cost wobble, which trains people to dismiss permanently. Too loose and a finding that grew 10× stays buried. Start with the ±25% log bands above, then measure: if the reopen-then-immediately-redismiss rate exceeds ~15%, the bands are too tight.

**Tenant isolation.** Every index is `tenant_id`-prefixed above; pair that with RLS rather than relying on the query layer, since one missing `WHERE` clause in a reporting endpoint is all it takes.

The shape that matters most: `disposition` in the POST response. Once agents get told what happened to what they emitted, everything downstream — dedupe rates, dismissal churn, materiality tuning, agent drift — becomes measurable instead of anecdotal.

## The DDL gap is the real finding here

`@DataJpaTest` validating Hibernate DDL rather than Flyway isn't a MySQL quirk, it's a permanent hole — every future migration has the same blind spot. Two things worth doing now while it's fresh:

**Testcontainers for the migration path.** One test class, real MySQL image, Flyway runs to head, then assert the schema: index existence, key lengths, charset, nullability. It's slow, so keep it separate from the 71 fast tests and run it on push rather than per-save. The assertion that would have caught 1071 is cheap:

```sql
SELECT index_name, SUM(sub_part IS NULL AND
       CASE WHEN data_type IN ('varchar','char')
            THEN character_maximum_length * 4 ELSE 8 END) AS bytes
FROM information_schema.statistics s
JOIN information_schema.columns c USING (table_schema, table_name, column_name)
WHERE table_schema = DATABASE()
GROUP BY index_name
HAVING bytes > 3072;
```

Run it as a schema invariant after every migration, not just this one.

**Migration rollback rehearsal.** You hand-cleaned a half-applied V6 — dropped tables, deleted the `success=0` row. That worked because V6 was additive and nothing depended on it yet. ## On prefix indexes specifically

`subject_id(191)` is fine for the unique constraint on `idempotency_key` — that's a hash, fixed width, high entropy in the first 191 chars. It's less fine for `finding_by_subject` if your subject IDs are ARNs, because ARNs share long prefixes:

```
arn:aws:ec2:us-east-1:123456789012:volume/vol-0a1b2c3d
arn:aws:ec2:us-east-1:123456789012:volume/vol-0e4f5g6h
```

191 chars covers those, but an EKS pod ref or a long resource path could collide past the prefix and turn index lookups into scans over a bucket. Cheap check: `SELECT COUNT(DISTINCT LEFT(subject_id,191)) / COUNT(DISTINCT subject_id)` once you have volume. If it drops below ~0.99, store a `subject_id_hash BINARY(32)` and index that instead, keeping the full `subject_id` as a non-indexed column. Same fix applies to `service_ref` if you ever index it alone.

## Ordering the three unbuilt pieces

Your reasoning on the reaper is right, and it generalises — here's how I'd sequence:

**1. `subject_scope` population.** Blocks the reaper, and it's the piece with the most design left in it. The question you have to answer per agent: what does a run *claim* to have covered? Alert Quality is easy — an explicit rule ID list, or a predicate like `{"kind":"alert_rule","all":true}`. FinOps is harder, because a run over one billing account doesn't cover resources in another, and a run that timed out halfway covered an undefined subset. Two rules that keep this honest:

- `subject_scope` is written at run *start*, as an intention, and narrowed at completion to what was actually evaluated. Never widened.
- `status: partial` writes the scope it actually covered, and the reaper skips partial runs entirely regardless.

**2. REST layer.** Unblocks everything human-facing: dismissal can't exist without `POST /findings/{id}/dismiss`, and until dismissal exists the TTL machinery you built is untested in anger. Start with `GET /findings`, `POST /findings`, and the dismiss pair. `/observations` and `/transitions` can wait.

**3. Expiry sweeper.** Smallest of the three and independently testable — it only needs suppressions to exist, not runs. Could go before the REST layer if you want a quick win, though without dismissal endpoints you'd be seeding suppressions by hand to test it.

**4. Reaper.** Last, gated on (1) being populated by every agent that writes findings — not most of them. A single agent emitting findings without `subject_scope` means those findings either never reap (backlog grows forever) or reap on a scope that doesn't cover them (silent resolution). Worth an explicit guard in the reaper: skip any `agent_name` whose latest complete run has null or empty `subject_scope`, and emit a metric for it so the gap is visible rather than inferred.

---

## The constraint, made concrete

The reaper's candidate set is every `open`/`acknowledged` finding for an agent. At steady state that's thousands to tens of thousands. If `scope_covers()` is a row-by-row JSON evaluation in application code, the reaper becomes a nightly full scan plus N deserializations, and it degrades exactly as your backlog grows — worst when you most need it working.

So the real requirement isn't "a predicate language." It's: **the scope must be expressible as a SQL predicate over indexed columns on `findings`.** Everything else follows. Any construct you can't push into a `WHERE` clause is a construct that makes the reaper O(N) in application memory.

That rules out, immediately:

- Regex or glob matching on `subject_id`
- Arbitrary boolean nesting (`OR` of `AND` of `NOT`)
- Predicates over fields not denormalized onto `findings`
- Anything requiring a join to an external system at reap time

## The shape that survives

Three scope kinds, and deliberately no more:

```json
{ "kind": "all" }
```
The run claims to have evaluated every subject this agent owns. Alert Quality's nightly sweep. Coverage predicate is trivially true.

```json
{
  "kind": "dimensional",
  "subject_kind": "cloud_resource",
  "dimensions": {
    "environment": ["prod", "staging"],
    "service_ref": ["svc-checkout", "svc-cart"],
    "account_id":  ["123456789012"]
  }
}
```
Conjunction of disjunctions. Each key is a column on `findings`; each value list becomes an `IN`. Absent key means unconstrained on that dimension. This covers ~all real cases: FinOps runs per billing account, per region, per environment.

```json
{
  "kind": "enumerated",
  "subject_kind": "alert_rule",
  "subject_ids": ["rule-1", "rule-2", ...],
  "subject_id_count": 847,
  "subject_ids_digest": "sha256:..."
}
```
An explicit list. Necessary for runs over a hand-picked set, and for narrowing a `dimensional` scope at completion when the run only got partway through.

That's it. No nesting, no negation, no wildcards.

## Why no negation

`{"exclude": {"environment": ["prod"]}}` looks harmless and is the one that will eventually silently resolve your prod backlog. Exclusions are correct only if the exclusion set at reap time matches the exclusion set at run time, and environment tags change. An agent that skipped prod on Monday and a finding retagged to prod on Tuesday produces a scope that claims coverage it never had. Inclusion-only means the claim is always narrower than reality when data drifts, which is the safe direction.

Same reasoning kills wildcards. `svc-*` expands differently as services are created.

## Storage

`subject_scope` stays JSON for the record, but the reaper never reads it row-by-row. Materialize the enumerated case:

```sql
CREATE TABLE agent_run_subject (
  run_id        BINARY(16)   NOT NULL,
  subject_kind  VARCHAR(64)  NOT NULL,
  subject_id_hash BINARY(32) NOT NULL,   -- sha256 of subject_id, sidesteps prefix-index issue
  PRIMARY KEY (run_id, subject_kind, subject_id_hash),
  CONSTRAINT fk_run_subject_run FOREIGN KEY (run_id) REFERENCES agent_runs (run_id)
) ENGINE=InnoDB;
```

Add `subject_id_hash BINARY(32)` to `findings` now as a generated-on-write column — you already have the fix documented for the prefix-collision problem, and this makes it load-bearing earlier, which is cheaper than retrofitting it later against volume. Both tables hash the same way and the reaper joins on it.

Then reaping is one statement per kind:

```sql
-- dimensional
UPDATE findings f
JOIN agent_runs r
  ON  r.agent_name = f.agent_name
  AND r.tenant_id  = f.tenant_id
SET f.state = 'STALE',
    f.state_reason = 'not_reobserved',
    f.state_changed_at = NOW(6),
    f.updated_at = NOW(6)
WHERE r.run_id = ?                       -- the run driving this reap
  AND r.status = 'COMPLETE'
  AND f.state IN ('OPEN','ACKNOWLEDGED')
  AND f.last_seen_at < r.completed_at - INTERVAL 1 MINUTE
  AND f.last_seen_at < NOW(6) - INTERVAL ? SECOND    -- category reap_after
  AND f.subject_kind = ?
  AND f.environment IN (?, ?)            -- expanded from dimensions
  AND f.service_ref IN (?, ?);
```

```sql
-- enumerated
UPDATE findings f
JOIN agent_run_subject s
  ON  s.subject_kind    = f.subject_kind
  AND s.subject_id_hash = f.subject_id_hash
JOIN agent_runs r ON r.run_id = s.run_id
SET ...
WHERE r.run_id = ? AND r.status = 'COMPLETE' AND ...;
```

Both are index-driven. No application-side evaluation, no per-finding deserialization. `scope_covers()` stops being a function and becomes a query builder — and that's the actual answer to the constraint you named.

## Narrowing at completion

Your rule was: written at start as intention, narrowed at completion, never widened. Enforcing that in code rather than convention:

**Start** writes the intended scope and `status = RUNNING`. Nothing reaps from a running run, so intention is never load-bearing.

**Completion** writes the actual scope plus `status`. The narrowing check runs as a validation, not a trust:

- `all` → `all`: valid
- `all` → `dimensional` or `enumerated`: valid (narrowing)
- `dimensional` → `dimensional` where every dimension's value set is a subset: valid
- `dimensional` → `enumerated`: valid
- `enumerated` → `enumerated` where the ID set is a subset: valid
- anything → `all` when start wasn't `all`: **reject, mark run FAILED**
- `enumerated` → `dimensional`: reject — can't prove narrowing

The subset check on `enumerated` is why `subject_ids_digest` and `subject_id_count` are in the record. Full set comparison at scale is expensive; count-decreased-or-equal plus digest-changed is a cheap sufficient signal that something narrowed, and you can do the exact subset check only when counts are equal but digests differ (which should mean a bug).

A run that never calls completion gets swept to `status = FAILED` by a timeout job. Failed and partial both never reap, so the default on abandonment is "reap nothing," which is the direction that can't silently clear a backlog.

## The gap metric, made explicit

Your guard — skip any agent whose latest complete run has null or empty scope — needs the complement, or it's invisible:

```sql
SELECT f.agent_name,
       COUNT(*) AS unreapable_findings,
       MIN(f.last_seen_at) AS oldest_unseen
FROM findings f
WHERE f.state IN ('OPEN','ACKNOWLEDGED')
  AND f.last_seen_at < NOW(6) - INTERVAL 7 DAY
  AND NOT EXISTS (
    SELECT 1 FROM agent_runs r
    WHERE r.agent_name = f.agent_name
      AND r.tenant_id  = f.tenant_id
      AND r.status     = 'COMPLETE'
      AND r.subject_scope IS NOT NULL
      AND r.completed_at > f.last_seen_at
  )
GROUP BY f.agent_name;
```

Emit as a gauge per agent. Nonzero and growing means an agent is producing findings it can never retire, which reads as a healthy backlog right up until someone notices half of it is fiction. This is the metric that tells you whether the reaper is actually covering what it appears to cover — worth having before the reaper ships, not after.

## Migration ordering

Given forward-only and expand/contract, this lands as:

1. **V7** — `agent_run_subject` table; `findings.subject_id_hash BINARY(32) NULL`; backfill is a no-op on an empty table but write the backfill statement anyway so the pattern exists for the next one.
2. **Agent change** — every agent populates `subject_scope` at start and narrows at completion. Ship to all agents. Watch the gap metric go to zero and stay there through a full cycle of each agent's cadence — Alert Quality nightly is one day, FinOps might be a month for commitment findings.
3. **V8** — `subject_id_hash NOT NULL` once every writer populates it.
4. **Reaper** — with the per-agent skip guard and the gap gauge already reporting.

Step 2's soak is the one worth not rushing. The gap metric reading zero for a day proves nightly agents are fine and proves nothing about the monthly ones.

---

One thing I'd flag as genuinely undecided rather than settled: whether `dimensional` scopes need a `subject_kind` at all, or whether an agent can emit findings across multiple subject kinds in one run. Alert Quality is single-kind. FinOps arguably emits against `cloud_resource` and `service` in the same sweep, and if so, a run needs a list of scopes rather than one. That's cheap to support now (`subject_scope` as a JSON array of scope objects, reaper runs one statement per element) and awkward to retrofit once runs exist. Worth deciding before V7 rather than after.

## On agent-runtime declaring scopes

This is where the design meets three codebases that don't share your invariants, so the part I'd get right is making violations impossible rather than documented.

**The narrowing validation has to live server-side.** If `RunScopeService.complete()` is the only enforcement and agents call it through a client library, a Python agent that constructs its own HTTP request bypasses every rule you just built. The rejections — unknown dimension, empty array, severity, widening — all belong at the persistence boundary, and the client library is a convenience over that boundary, never the boundary itself.

**The multi-kind case is where agents will get it wrong.** `aws.public_exposure_auditor` has to declare `cloud_resource` and `principal` separately and narrow each independently at completion. The failure mode I'd expect: the run enumerates buckets and security groups fine, the IAM call throws, and the agent completes with a scope covering only `cloud_resource` — but `status: COMPLETE`, because from the agent's perspective it produced findings and finished. Now `principal` findings from previous runs reap against a run that never looked at them.

Two ways to close it, and I'd want both:

- Per-element scope status, not just per-run. If `principal` collection failed, that element is marked partial and the reaper skips that kind for that run, while `cloud_resource` still reaps normally. A run being all-or-nothing throws away good coverage every time one dimension flakes.
- The completion call names which kinds it covered, and the service rejects a `COMPLETE` status whose kind set is narrower than the declared intention unless the missing kinds are explicitly marked partial or skipped. Silent omission becomes a rejection instead of a coverage claim.

**Declaring scope at start needs to be structurally hard to skip.** If it's a separate call an agent makes before emitting, some agent will emit without it — and then `POST /findings` has to decide whether to accept verdicts with a `run_id` that has no scope. I'd make `run_id` mandatory on verdict ingest and have run creation return it, so an agent physically cannot emit findings without having opened a run. The scope declaration rides on the create call. That also gives you the enforcement point for `stable_key: false` rejection you already have, in the same place.

1. **Server-side validation complete** — narrowing, dimension whitelist, empty-array, derived-field rejection, all enforced at the boundary with tests that bypass the client library.
